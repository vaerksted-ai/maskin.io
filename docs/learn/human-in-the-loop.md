# Human in the loop: the approval gate before side-effecting tool calls
**Four major agent-SDK vendors shipped the same primitive in 2025-2026: a named contract that pauses an AI agent before it invokes a tool that would act on the world.** OpenAI calls it `needs_approval`; Cloudflare calls it `waitForApproval()`; Microsoft calls it `RequestPort`; Temporal expresses it as a signal on a durable workflow. Four API surfaces, one primitive. If you are building an agent that sends the email, moves the money, or files the ticket, this is the contract buyers now expect you to hold.
## The primitive, in one sentence
Before an agent calls a tool marked as side-effecting — anything that would change something outside the model’s own scratch space — the run pauses and waits for a person to approve or reject. Nothing ships until someone says so. That is the whole contract; everything else is which API surface names it.
The older meaning of “human in the loop” — labeling training data for supervised learning — is still valid, but agent builders in 2026 reach for the phrase to name this pause-before-side-effect contract instead. Both meanings are alive; the phrase now defaults to the second when the context is agents.
## Four vendors, four API surfaces
The convergence is what makes this a category, not a feature. Every major agent framework shipped the same primitive between the OpenAI Agents SDK launch in March 2025 and the Microsoft Agent Framework preview in early 2026 — each with a different name, all with the same behaviour.
- **OpenAI Agents SDK** marks a tool with `needs_approval`. When the agent selects it, the SDK returns a `RunState` object rather than executing — the state can be serialised, held for a human decision, and later resumed with the approval or rejection recorded on the run.
- **Cloudflare Agents** exposes `waitForApproval()` inside a Workers-hosted agent. The Worker suspends, the request lands on an approval surface (an MCP elicitation, an inbox, a Slack message — the surface is your call), and the Worker resumes on the returned decision.
- **Microsoft Agent Framework** models the approval channel as a `RequestPort` — a typed input port on the agent graph that a human (or a governance service) fulfills before the downstream node runs.
- **Temporal** wraps the same pattern in a signal-based approval activity: a durable workflow reaches the approval activity, blocks on a signal, and continues when the signal arrives with the decision payload.
The four names are noise; the primitive is signal. Any of them will pause the run and hold state until a human makes the call. What differs is where the state lives, how long it can wait, and how the approval request is surfaced — and those are the design decisions that separate a demo from a system you would run in production.
## Why the primitive appeared now
Agents crossed the line from “returns a chat response” to “calls a tool that acts on the world.” The old shape — a model that produces text and a human that reads it — had implicit oversight built in: the human decided what to do with the text. The new shape — a model that invokes tools that send emails, mutate rows, transfer money — has no implicit gate. Something has to hold the tool call before it commits, or the wrong side-effect ships automatically.
Vendors reached the same design at nearly the same time because the failure mode was the same everywhere: an agent that autonomously called a side-effecting tool in a demo, and the demo audience realised the fix could not be “write a better prompt.” The fix had to be a contract at the SDK layer, callable per tool, and readable by the operator without reading the model’s reasoning trace.
## What the primitive does not do
The pause is necessary, and it is not sufficient. The primitive answers “did a human approve this action?” It does not answer:
- **Was the reason recorded next to the work?** If the approve/reject click is the only artefact, no one downstream can tell why the decision went that way. The reason lives in the reviewer’s head, not the run.
- **Can another agent, another loop, or a future operator read the decision?** An SDK primitive holds state for the run it belongs to. When the run ends, the decision typically disappears unless something outside the SDK persisted it.
- **What is the audit trail across tools?** An agent that touches four tools produces four independent approval records — unless something above the SDK is stitching them into one narrative.
Those are the three questions that separate an SDK pause from real oversight. The primitive is the wire; what carries the decision across time and across tools is a different layer.
## What a workspace-shaped gate adds
The pause-before-side-effect contract is the floor. The design decision that sits on top is *where the decision gets recorded so the reason survives the run*. In a workspace-shaped implementation, the approval is not a click that resumes the SDK — it is a change to a typed object with the reviewer’s note attached, and the SDK resume is a consequence of that change. Plain-English: the decision is recorded next to the work it approves, so anyone can go back and read what was decided and why.
That naming matters because it is what turns the pause into an audit trail without a second system. The event that resumes the agent is the same event an auditor reads six months later — a typed workspace object (a “bet,” a “task,” a “send”) with the approve/reject transition and its reason on the object’s own event log. There is no separate approvals database to keep in sync, and no reviewer’s prose stuck in a Slack thread the SDK has never heard of.
This is the shape the [stateful orchestration substrate](/docs/what-is-a-stateful-orchestration-substrate/) was designed to hold: a shared typed store where handoffs between stateless agents survive, so a pipeline produces coherent work across runs. An approval-gate decision is one class of handoff — from the agent that proposed the action to the human who ruled on it — and the substrate keeps it addressable long after the run that produced it ended.
**Maskin loops carry typed outcomes and verdicts that persist across tools, not recurring workflow execution inside one product.** The approval is not a modal that blocks a UI — it is a first-class transition on a first-class object. Loop-level pause, per-action-class autonomy, and per-loop override rate are consequences of the same substrate, covered in the companion piece on [AI agent governance for small teams](/docs/learn/ai-agent-governance/).
## Approval surfaces, in the wild
The primitive is neutral on where the human sees the approval request. In practice, four surfaces dominate as of 2026, each with a different failure profile:
- **Inbox surfaces.** A queue of pending approvals with a per-item context panel. LangChain’s open-source [Agent Inbox](/docs/agent-inbox/) is the definitional reference for this shape — three interrupt types (notify, question, review), one queue, one operator. Scales while the queue is short; buckles when many parallel loops share it and the operator has to remember what each item was for.
- **Chat surfaces.** The approve/reject arrives as a Slack message or a Teams card. Fastest response time when the reviewer is at their desk; worst audit trail, because the reason for the decision lives in the chat scrollback and rarely makes it back onto the run.
- **MCP elicitation.** The agent asks its host client (Claude Desktop, Claude Code, another MCP-native client) for the human’s call, in-context. Cleanest when the human is already driving the agent through an MCP client; irrelevant when the agent is running headless.
- **Workspace-graph surfaces.** The approval is a status transition on the object itself — the same object the work will land on. The [ambient agent workspace](/docs/ambient-agent-workspace/) pattern names this as the alternative to the flat inbox once you have many parallel loops. Slower to build than an inbox; the audit trail is a side effect of the work.
Which surface fits which loop is a judgment call about volume, reversibility, and how much context the reviewer needs. Most production systems end up running two or three at once — MCP elicitation for the operator’s own driven loops, inbox for the queued ones, workspace-graph for the ones an auditor will read afterwards.
## How to hold the primitive without shipping theater
The trap the primitive does not prevent: *approval fatigue*. A reviewer with a long queue and low-context approve buttons learns to click approve, and the pause becomes a rubber stamp. The pause fires, the run resumes, and the audit trail records “approved” on an action nobody read. That failure mode is covered end-to-end in the companion piece — [Human in the loop AI: when it’s real, when it’s theater](/docs/learn/human-in-the-loop-ai/) — which walks the override-rate metric, the human-on-the-loop vocabulary cut, and what EU AI Act Article 14 actually requires. Read that piece for the register on when a pause counts as oversight.
The short version: pair the primitive with three things and it holds up under audit. First, **tier the gate per action class** — not every tool call needs the pause, and forcing the pause everywhere is what produces the fatigue. Second, **watch override rate per class over time** — 0% is rubber-stamping, above 20% is a broken model, real oversight sits in the middle band. Third, **record the reason on the object**, not on the SDK — so a reviewer six months later can reconstruct what was decided and why without reading a model’s reasoning trace.

- **Four vendors, four API surfaces, one primitive.** OpenAI `needs_approval`, Cloudflare `waitForApproval()`, Microsoft `RequestPort`, Temporal signal-based approval — different names for the same contract.
- **The pause is necessary and not sufficient.** A click that resumes a run is not the same as a recorded decision an auditor can read six months later.
- **What a workspace-shaped gate adds is persistence and audit.** The approval is a transition on a typed object — the decision is recorded next to the work it approves — not a modal that blocks a UI.
- **Four approval surfaces dominate:** inbox, chat, MCP elicitation, workspace-graph. Most production systems run two or three at once, tiered by action class.
- **Pair the primitive with override-rate monitoring** to avoid approval fatigue. The pause without the metric is theater.
## FAQ
### What is human in the loop?
In 2026 the phrase mostly names an SDK-level approval gate: before an AI agent calls a tool that would send an email, move money, or otherwise act on the world, the run pauses and waits for a person to approve or reject. Four major vendors — OpenAI, Cloudflare, Microsoft, and Temporal — shipped named primitives for exactly this in 2025-2026. The older meaning (data labeling for supervised learning) is still valid, but not what agent builders reach for the term to name.
### What is the approval-gate primitive?
A contract at the SDK layer: an agent about to invoke a tool marked as side-effecting suspends its own run, emits a request for approval, and only resumes when a human (or another authorised actor) returns an approve or reject. It is the same shape across every vendor that named it: OpenAI’s `needs_approval` flag with `RunState` suspension, Cloudflare’s `waitForApproval()` call, Microsoft’s `RequestPort`, Temporal’s signal-based approval activity.
### Which vendors ship an SDK-level human-in-the-loop primitive?
As of 2026: OpenAI Agents SDK (`needs_approval` on tools, `RunState` for suspension); Cloudflare Agents (`waitForApproval()` and MCP elicitation on Workers); Microsoft Agent Framework (`RequestPort` as the approval channel); Temporal (signal-based approval activities on a durable workflow). Four vendors, four API surfaces, one primitive — that convergence is the story.
### Is human in the loop the same as human oversight?
No — and the difference matters. Human in the loop is a technical contract that pauses a run. Human oversight (the standard EU AI Act Article 14 uses) is a broader design property that also covers monitoring, understanding, and halting. A pause without a recorded decision does not deliver oversight; oversight without a pause on side-effecting actions is not enforceable. The two live at different layers.
### What does a workspace-shaped approval gate add over a plain SDK primitive?
Persistence across tools plus an audit trail. An SDK primitive pauses one run inside one product. A workspace-shaped gate records the decision as a typed outcome next to the work it approves, so the reason for the approval survives the run — and any other agent (or auditor, or the same loop tomorrow) can read what was decided and why.
### How is this different from human-on-the-loop?
Human-on-the-loop puts the person above the transaction as a supervisor; human-in-the-loop puts them inside it as the trigger. The vocabulary cut, safety register, and EU AI Act Article 14 reading are covered in the companion piece on [Human in the loop AI: when it’s real, when it’s theater](/docs/learn/human-in-the-loop-ai/). This page is about the SDK primitive; that page is about the vocabulary and the metric.
