What this workflow gets you

The LLM knowledge wiki workflow closes the gap between “we know this internally” and “every agent in the workspace knows this the moment it’s written.” A knowledge space like Notion or Obsidian is a good place for humans to write; it stops before the bet, because a page is not the object of work — it’s a note about the work. This loop takes the note, links it to the decision it supports, and makes it part of the citable substrate.

  • Answers are grounded, with citations. When an agent responds using the wiki, the source is a typed object in the graph you can open, not a paraphrase from a black box.
  • The wiki is queryable, not just readable. Every entry is a first-class object with typed relationships — who wrote it, which bet it supports, which decisions it contradicts, when it was last verified.
  • Stale entries surface themselves. The observability layer flags when an agent cites an entry that hasn’t been touched in six months and the underlying decision has shifted. Curators get a task; the wiki self-audits.
  • It composes with every other loop. Because the wiki is on the same typed object graph as the SEO loop and the sales loop, agents in those loops cite it natively; you don’t maintain three separate knowledge stores.

The six-step loop the video walks through

  1. Capture. Knowledge lands from Slack threads, shipped bets, decision comments, or a human writing directly into the workspace. Each becomes a typed knowledge object with an author and a linked context.
  2. Structure. A curator agent proposes a shape — canonical entry, related-to links, contradicted-by links, verify-by-date — and a human approves before it lands in the wiki.
  3. Index. The entry is embedded and its relationships written to the graph. It’s immediately citable by every MCP-connected agent in the workspace.
  4. Cite. When an agent answers a question — in a comment, a session, an outbound draft — it cites the specific entry it drew from, linked in the response. Answers without a citation are visibly ungrounded, so the pattern surfaces its own gaps.
  5. Verify. Curators periodically re-open aged entries; a task fires when an entry’s verify-by date lapses or a downstream decision contradicts it.
  6. Retire. Superseded entries are marked, not deleted — the graph keeps the history, and agents can walk the supersession chain when the reason matters.

What this workflow runs on

Below the fold on purpose: the loop is what closes, the primitives are just the parts. Naming them here so you can copy the shape.

  • Loop: the knowledge wiki loop — a persistent Maskin loop that carries state across capture, structure, index, cite, verify, and retire.
  • Agents: Knowledge Curator (proposes structure and verify-by dates), Knowledge Publisher (indexes approved entries), Knowledge Auditor (surfaces staleness and contradiction).
  • MCPs: the Maskin MCP server (the object graph itself), Slack (capture from thread context), an embeddings MCP (for the citation index).
  • Skills: capture-from-slack skill, structure-entry skill, verify-entry skill, cite-with-source skill.

Why this beats a knowledge space with an LLM plugin

Obsidian, Mem, Confluence, and their siblings own capture and retrieval; they stop before the bet. The failure mode of “knowledge space + AI plugin” isn’t retrieval — it’s that the page has no win condition and no relationship to the decisions it should support, so the AI plugin generates plausible-sounding paraphrases with no way to close the loop when the underlying decision changes. This workflow lives in the workspace-graph tier: every entry is linked to the bet, task, or decision it supports, and staleness surfaces itself.
