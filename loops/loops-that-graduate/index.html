The agentic loop trust ladder: when an agent can stop being checked

An agent can stop being checked on every output only after it clears a written quality bar across a long enough run of real work, a named human signs off, and you can return it to supervision. Keep checks and a demotion path active once the agentic loop runs unattended.

Key takeaways
  • Write the quality bar and acceptance criterion for each output before the first run.
  • Dry-run against past real cases before allowing the loop to handle live work.
  • Require review of every output while the loop is supervised.
  • Before removing per-output review, set a minimum run, a fault threshold, and a named sign-off owner.
  • Keep checks active on every output and define the trigger and route back to supervision.

What an agentic loop is

An agentic loop is a repeatable process with an entry, typed records, quality gates, and a close that produces work again and again. Because the process keeps producing outputs, its quality check has to keep running too.

The trust ladder

Think of agent autonomy levels as rungs on a spectrum, not as a switch. A loop starts under supervision. It can earn the ability to move work forward without a check, and it can be pulled back when its results no longer meet the bar. Paused is reachable from any rung. The exact set of states is configurable per workspace, so use names and transitions that make sense for your process.

The names matter less than the rules. Supervision does not mean “almost ready”: it means no output is trusted to move work forward unchecked. The record of every critique and sign-off is what lets you see, later, why the loop reached its rung.

How a loop earns a rung

Start by defining what good means for this loop. Set a quality signal that is more than a feeling, an acceptance criterion for one output, and a bar for a run of outputs. The worked example below puts numbers on this. The point is to choose criteria before reviewing results, rather than adjust the bar to make a struggling loop look healthy.

Then close every run with a critique. A reviewing agent should have a typed role tied to the class of output it checks. It compares the output with the loop’s rubric and the acceptance criteria declared by the decision that started the work. It cites the check in the loop’s history. That critique is evidence you can examine, not a reassuring status light.

Do not ask a model a question a schema can answer. If the check is whether a reply cites an article that exists, whether a required field is filled, or whether a number stays under its cap, run a deterministic check. Use those checks wherever the question can be reduced to a schema check. They do not drift, tire, or argue their way to a pass. Use a reviewing agent where a deterministic check cannot settle the question, and escalate to a human when neither can make the call cleanly.

Keep the reviewer accountable too. Track whether its flags hold up for this class of output. If its critiques stop landing, the reviewer itself needs to be demoted. A reviewer without a track record is not a reliable gate just because it has the title of reviewer.

Before you let a loop run unattended:

  • Choose a quality signal that is more than a feeling.
  • Assign a reviewer for each class of output.
  • Use deterministic checks first where a schema can decide.
  • Name the human who ratifies graduation.
  • Define how to move the loop back down.
  • Write the outputs and decision to a record.

This is a practical extension of AI agent governance: authority should follow evidence, and there should be a person accountable for granting it. For more on where review belongs in a process, see human in the loop for CTOs.

A worked example: a support reply loop

This is an illustrative example with made-up numbers, not a customer result and not a benchmark.

The loop drafts replies to tier-1 support tickets at a SaaS company: password resets, billing dates, and how-do-I questions. Before its first run, the head of support writes the quality bar: a reply is faulty if a reviewer would have to rewrite it, it cites no existing help article, or it promises anything outside written policy, including refunds, dates, or credits. The head of support is the named human who ratifies changes in rung.

Before a reply can leave the loop, deterministic checks that use no model verify that it cites a real help-article ID, contains no refund or credit amount, and stays under the length cap. A reviewing agent critiques tone and accuracy on every reply. These checks do not replace the written quality bar; they cover specific failure modes, while review catches problems the checks cannot establish.

The team uses this step-up gate to move from supervised to autonomous:

  • At least 300 replies over at least 3 weeks.
  • A fault rate at or below 2%, which means at most 6 faulty replies.
  • Zero policy-breaking promises and 100% pass on deterministic checks.
  • Before signing, the head of support reads the 5 worst critiques.

Once autonomous, tier-1 replies go out without per-reply review. The deterministic checks and reviewing agent still run on every reply, and the head of support spot-checks 20 replies a week. The team demotes the loop if the fault rate goes above 4% on any rolling 100 replies, or if it sends any single policy-breaking promise. Either trigger returns it to supervised the same day. Returning to autonomous requires a fresh run of 150 replies at 2% or lower.

In week 5, the refund policy changes and the help article is rewritten, but the loop keeps citing the old article. On day 4, 7 faulty replies in a rolling 100 trip the 4% trigger. The loop drops to supervised, and the head of support signs the demotion. The article mapping is fixed; after 150 clean replies, the loop is promoted again.

Replace the thresholds, sample size, review cadence, and sign-off owner with the values your team can defend.

Who decides: humans set the bar, agents watch

Humans define the quality bar when the loop is created: what it should produce, what a good output looks like, and what must hold across a run of outputs. A machine should not choose a threshold that decides whether its own process is safe to trust. A human also ratifies graduation and demotion. Promoting a loop is a governance decision, and the person who signs off should be the person accountable if the call was premature.

Agents do the watching that a human cannot sustain across many outputs. They can look for drift, compare a fault pattern with loops previously pulled back, and challenge a human who wants to raise the bar simply to make weak results appear acceptable. This is the division of work: humans direct, agents detect. An agentic workspace can make the process easier to reason about, but the decision about the bar still belongs to people.

Why demotion is the safety mechanism

Graduation without a way back down turns autonomy into a one-way bet. A loop can meet its bar and later stop meeting it. Quality can fall, or the reviewer’s fault rate can climb above the threshold. In either case, demote the loop to supervision, where it keeps running under review until it earns its way back or the team retires it.

That is why the gate must keep running after graduation. Quarterly or sprint retrospectives alone leave long stretches in which poor outputs can go unnoticed. Execution volume is not health, and a green dashboard is not a quality signal. Define who owns a demotion decision and record it: pulling a running process back can have downstream effects, so someone must own that call.

The trap: a reviewer that can be argued down

If the reviewer is a language model and the person running the loop knows it can be argued down, graduation can become a negotiation. The reviewer flags a fault, the user pushes back, the reviewer softens, and the loop gets promoted. The bar did not move; the reviewer did. This is most dangerous at the point where someone has the strongest incentive to argue for autonomy.

Use three counter-moves. First, use deterministic checks wherever the fault reduces to a schema check. A number is a number. Second, where determinism runs out, require human ratification and show the human the strongest opposing critique, not a tidied summary. The person signing off should read the hardest version of “no” before saying yes. Third, use typed-role reviewers with track records. Keep their history of held-up and argued-down critiques, and demote reviewers when their flags stop landing.

These safeguards make it harder for throughput to become the reviewer’s hidden incentive. They also give you something concrete to inspect when deciding whether a loop should remain supervised, graduate, or be pulled back.

Loop autonomy vs agent autonomy

An agent can be capable while the loop that uses it is still not trustworthy enough to run unattended. Trust attaches to a repeatable process measured over many outputs, not to a model in isolation. A strong output does not show that the next output will meet the bar, or that the review process will catch a fault. For autonomous agents, trust is therefore about the loop’s record and gates, not a general claim about a model’s ability.

This distinction helps you decide what to authorize. You are not declaring that an agent is safe for every task. You are deciding that this loop, with its defined entry, records, quality checks, and close, has earned a particular rung. Keep the scope tied to that process.

FAQ

What is an agentic loop?

An agentic loop is a recurring workflow in which an agent produces an output, that output is checked against defined criteria, and the result is recorded before the next run. The useful unit to govern is the whole workflow, including its inputs, checks, reviewer, and stop conditions, rather than one impressive response.

How does an agentic loop work?

A loop starts from a defined request or event, gathers the needed records, produces work, runs quality gates, and closes with a recorded outcome. The team can inspect those records to see where an output failed and whether the gate caught it. For example, deterministic checks can verify required fields while a reviewer judges tone.

How do you make an agent autonomous safely?

Set the acceptance rule before testing, then run the loop on real work under review. Promote it only after a specified volume and duration meet the fault limit, required checks pass, and a named owner signs off. In the support example, that meant 300 replies over at least 3 weeks, with faults at or below 2%, plus a defined route back to supervision.

What are agent autonomy levels?

A practical ladder is draft, supervised, and autonomous, with paused available from any rung. Draft produces work for review; supervised requires review before each output goes out; autonomous removes that per-output review while ongoing checks remain. The set of rungs can be configured per workspace. A level describes how much a loop and its record permit without a check, not a property of the model.

When should a loop be demoted?

Demote a loop when it crosses a pre-agreed fault threshold, breaks policy, or loses a control needed for its current rung. Set the trigger and destination before unattended operation begins, so the response is not improvised during an incident. In the worked example, more than 4% faults in a rolling 100 replies or one sent policy-breaking promise returns the loop to supervised.

Does a human stay in the loop once it is autonomous?

Yes, but not necessarily as a reviewer of every output. The human owns the quality bar, authorizes promotion, samples outputs, and can demote or pause the workflow. Checks should continue on every output, and the owner should review whether those controls are still adequate when policy, source material, or the work itself changes.
