The LLM knowledge wiki workflow

Meetings, chat, and docs in. An evergreen wiki your team and your agents both cite, out. Typed objects, linked context, one shared surface — entries stay current because the triggers that captured them re-run when the source updates. No stale pages, no scattered context, no hallucinated citations.

What it does

The LLM knowledge wiki workflow captures the raw context your team already produces — meeting transcripts from Zoom or Gong, Slack threads, doc updates, PR merges, CRM notes — and turns each stream into typed, linked entries on a shared object graph. A librarian agent reads new signal, decides whether it belongs on an existing entry or deserves a new one, drafts the update, and files it. Because entries are typed and linked (not just tagged), an agent asked "what did we decide about <topic>?" can walk the graph in one call rather than search-and-summarise across many. And because the triggers that captured an entry re-run when the source changes, the wiki stays current without a page-refresh party every quarter.

Who it's for

Chiefs of staff, founders, and any team whose institutional knowledge is scattered across five tools and one long-tenured senior. The workflow is built for the team that wants a single evergreen source of truth their agents can cite in-context without hallucinating and their humans can trust without spelunking through last quarter's Slack. If you already have a place where meetings, chat, and docs happen, this workflow sits above them and gives the outputs a graph.

What closes the loop

The loop closes when an entry is cited — by a human or an agent — and the citation resolves against a live entry that is still true. The metric is coverage: what share of "what do we know about X?" questions asked in the workspace resolve to a linked wiki entry within one hop, versus falling back to a full-text search or a hallucination. That number goes up as the wiki grows and stays up because the triggers keep the entries current. Stale entries fall in coverage and get proposed for refresh automatically.

How it works (below the fold)

The workflow is composed from four primitives that ship in Maskin. If you're evaluating it as a system to run on your own instance, this is the shape of what's underneath.

  • Loop

    Knowledge wiki loop

    Steps: capture → classify → file → link → refresh. Runs continuously; humans stay on curate + trust.

  • Agent

    Librarian

    Decides whether new signal updates an existing entry or deserves a new one; drafts the update and files it.

  • Agent

    Meeting Summariser

    Reads transcripts (Zoom, Gong, Fathom), pulls decisions and open questions, hands them to the librarian.

  • MCP

    Slack + Gong + Notion + GitHub

    Capture surface. Read-scoped by default; write access is opt-in per source. All auditable in the workspace.

  • Substrate

    Typed object graph

    The wiki lives as typed objects with typed relationships, not as free text. Agents traverse the graph in one call.

  • Trigger

    Freshness sweep

    Weekly walk over entries; proposes refresh tasks on any entry whose source has changed since it was last written.
